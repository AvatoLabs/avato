# Docs / File / Source Set 信息架构方案 V2

**状态**：提案  
**视角**：UIUX 审计 + 信息架构优化  
**范围**：`/docs`、`/content/source-sets`、文档与文件的对象模型、列表与详情导航、规模化后的可用性  
**目标**：从飞书式工作区心智出发，把“文档工作区”“资料集容器”“原始文件资产”三者彻底拆清，避免继续在一个半对称对象模型上堆 UI

---

## 一、执行摘要

上一版方案方向是对的，但还不够成熟。

对的地方在于：

- 没有把 `Docs` 和 `Source Set` 硬并成一个入口
- 认识到了 `Doc` 和 `File` 不是同一种对象
- 认识到了 `Source Set` 不应该只是一个文档标签

不够成熟的地方在于：

- 还是把太多组织压力压进了窄 sidebar
- 还没有彻底区分“全局导航”“范围选择”“对象列表”“对象详情”
- 还没有把 `Doc / File` 的产品语义从“能不能互转”提升到“它们分别是什么”
- 还没有把当前现有双栏布局转成更像飞书的任务流

V2 的核心结论是：

1. `Docs` 与 `Source Set` 保持双入口，不合并。
2. `Docs` sidebar 不负责承载所有文档树，只负责“范围选择”。
3. `Docs` 主区负责展示当前范围下的文档列表或文档详情。
4. `Source Set` 首页是容器入口页，不是混合文件树。
5. `Source Set` 内部拆成 `Overview / Docs / Files` 三个工作面。
6. 对用户不要讲“Doc 和 File 可以互转”，而应该讲“文件可生成文档，文档可关联来源文件”。

## 二、审计方法

本次优化从三套标准同时出发：

### 1. 飞书式工作区心智

核心特征不是“长得像飞书”，而是这些产品规律：

- 全局导航稳定，不承载全部内容树
- 场景内导航局部化，不把所有分类塞在一层
- 最近、收藏、常用范围优先于全量目录
- 对象列表和对象详情分离
- 容器首页承担“理解场景 + 进入任务”的职责

### 2. UIUX 基本原则

- 窄 sidebar 只做高频切换，不做重信息密度浏览
- 大规模列表应放在主区，不应全压在 240px 左右的侧栏
- 用户需要先知道自己在哪个“范围”，再知道自己在看哪个“对象”
- 结构应该服务任务，而不是服务数据模型

### 3. 当前实现约束

当前 `docs` 已经是标准两栏：

- 左侧 `Sidebar`
- 右侧主区 `Outlet`

并且要特别区分：

- 左侧 sidebar 已经承担了文档列表导航
- 但 `/docs` 根路由主区仍然是创建型 placeholder，不是 scope 列表工作台

也就是说，当前产品状态不是“`/docs` 已经完全是工作台”，而是：

- `sidebar` 已经有列表能力
- `main content` 还没有被定义成范围列表页

所以最合理的演进，不是再把左侧改成一棵更复杂的树，而是：

- 左侧退回成“范围导航”
- 右侧主区承担“列表页 / 详情页”

## 三、对 V1 方案的审计结论

### [P1] 把按 Source Set 分组后的文档列表直接塞进 Docs Sidebar，规模化后仍然会乱

V1 虽然已经从“纯平铺列表”进了一步，但如果继续让 sidebar 同时承担：

- Source Set 分组
- 组内文档列表
- 搜索结果入口
- 最近项
- 未归属项

那文档一多，侧栏依然会失控。

问题本质不是“有没有分组”，而是“窄栏不该承载全量对象浏览”。

### [P1] V1 还没有彻底区分四个层级

产品上至少有四层东西：

- 全局入口
- 当前范围
- 当前范围内对象列表
- 当前对象详情

V1 虽然有信息架构意识，但还没有把这四层彻底拆开。

这会导致：

- Sidebar 既像全局入口，又像局部列表
- Source Set 既像容器，又像过滤条件
- `/docs` 根页像首页，又像空态页

### [P1] “Doc / File 半对称关系”已经被识别，但用户语义还不够干净

当前实现里：

- `file -> doc` 明确成立
- `doc -> file` 只在特定上下文成立

如果产品继续讨论“互转”，就会把实现细节错当成产品语义。

对用户更准确的语义应该是：

- 文件可生成文档
- 文档可关联来源文件
- 导出为文件是另一种动作，不是“转回文件对象”

### [P2] “未归属”不应该只是一个平行分类，更应该被定义成整理收件箱

V1 把 `Unassigned` 当成一个普通过滤器是正确的第一步，但还不够。

更成熟的定义应该是：

- `未归属` 不是稳定归宿
- 它是一个待整理池
- 它在产品心智上更像 inbox，而不是 permanent category

### [P2] Source Set 首页不能只回答“这里有什么”，还要回答“我现在该做什么”

如果 Source Set 首页只是一组卡片或一个概览页，它还不够像工作区。

它还需要承担：

- 最近活动
- 快捷入口
- 当前资料集内最常用动作
- 从容器进入 Docs / Files 的分发

## 四、重新定义三类对象

## 1. `Doc`

`Doc` 是知识对象，不是资产对象。

职责：

- 写作
- 编辑
- 阅读
- 协作
- 沉淀知识结果

它是工作结果层。

## 2. `File`

`File` 是资产对象，不是知识对象。

职责：

- 上传
- 存储
- 预览
- 下载
- 解析
- 参与检索与 RAG

它是工作材料层。

## 3. `Source Set`

`Source Set` 是工作容器，不是标签，也不是文件夹。

职责：

- 组织围绕某个主题的一组 `Docs` 与 `Files`
- 形成一个可检索、可协作、可消费的知识工作场景
- 承担知识输入、整理、沉淀、复用

它是工作场景层。

## 五、当前实现中的真实关系

从现有代码看，当前系统更接近下面这个结构：

### `file -> doc`

成立。

- 文件可通过解析进入文档编辑器
- 已有 `document.ensureFileDocument` tRPC mutation，对应 `DocumentService.ensureFileDocument`
- 已有 `document.parseDocument` / `document.parseFileContent` 路由，对应 `parseDocument(fileId)` / `parseFile(fileId)` 服务实现

### `doc -> file`

不全量成立。

- 只有在某些创建路径中，文档会创建 mirror file
- `/docs` 根创建的普通文档，通常没有对应 file
- folder 是 document-only

### 产品结论

当前不应该继续说：

- “Doc 和 File 能自由互转”

而应该统一成：

- `File` 可以生成 `Doc`
- `Doc` 可以关联来源 `File`
- `Doc` 与 `File` 可以同归属于某个 `Source Set`

## 六、版本语义与“来源文件关联”的边界

如果“文档关联来源文件”这句话没有定义清楚，后面一定会造成版本混乱。

### 1. 混乱会发生在什么地方

如果产品语义被理解成下面任一项，就会出问题：

- 改了文档，来源文件也应同步变化
- 改了来源文件，文档也应自动同步变化
- 文档和文件是同一对象的两种视图

这三种理解在当前模型里都不成立，也不应该成立。

### 2. 当前实现已经说明它们不是同一版本对象

从现有代码看，带 `fileId` 的文档在更新时，只会同步文件的部分元数据：

- 标题改动时同步 `file.name`
- 父级改动时同步 `file.parentId`
- 内容改动时同步 `file.size`
- 并触发 file chunk reindex

但它不会把编辑后的文档内容反写回原始二进制文件本体。

也就是说，当前实现更接近：

- 文档在消费文件
- 文件在提供来源与检索载体
- 二者有关联，但不是同一份版本内容

### 3. 正确的产品定义

“关联来源文件”应该被定义为 **provenance（来源关系）**，而不是 **live sync（实时双向同步）**。

更准确的语义是：

- 这篇文档最初来自哪个文件
- 这篇文档当前是否仍参考该文件
- 如果来源文件有变化，用户是否要重新导入或重新提取

而不是：

- 这篇文档和该文件永远是同一版本

### 4. 推荐的版本模型

最稳的做法是三层语义：

- `来源文件`：原始材料，默认视为输入快照
- `派生文档`：从该输入提取、整理、继续编辑后的知识对象
- `导出文件`：把当前文档导出成一个新文件，是新的输出，不是回写原来源文件

这三者不要混成一个对象。

### 5. UI 上应该怎么表达

文档页可以展示：

- `来源：xx.pdf`
- `导入时间：2026-03-30`
- `状态：已从来源脱离 / 可重新导入 / 来源已更新`

但不要展示成：

- `与来源文件保持同步`

除非后面真的实现了明确的同步规则与冲突处理。

### 6. 如果以后要支持“重新同步”，也必须是显式动作

如果未来真的要支持来源文件更新后影响文档，建议只做下面这种显式交互：

- `重新提取内容`
- `生成新版本草稿`
- `对比来源更新`

而不是静默自动覆盖。

原因很简单：

- 文档往往已经被人工整理、删改、重写
- 一旦自动覆盖，用户会丢失编辑成果
- 这会比“没有同步”带来更大的信任问题

### 7. 最终结论

所以“文档可以关联来源文件”本身没有问题。  
真正危险的是把这种关联误定义成“版本绑定”或“自动同步”。

最优雅的设计应该是：

- `来源关系` 可见
- `版本关系` 默认解耦
- `重新导入/重新提取` 是显式操作
- `导出为文件` 是新产物，不回写原来源

## 七、导入规则：入口决定对象形态

为了避免继续复杂化，导入规则应该足够简单，而且一眼能讲明白。

推荐直接定成下面这条产品原则：

### 原则

- 在 `Docs` 入口导入内容，结果是 `Doc`
- 在 `Files` 入口上传内容，结果是 `File`

不要让同一个入口同时承担“保留文件形态”和“转成文档”两种默认结果。

### Markdown 的处理规则

对于 `.md / .markdown`，建议明确成：

- 从 `文档页 / Docs 工作区` 导入：直接成为文档
- 从 `Files / 资料集文件区` 上传：保持为原始 Markdown 文件

也就是说：

- `Docs` 面向知识对象
- `Files` 面向资产对象

入口本身就应该告诉用户“你在创建什么”。

### 为什么这条规则重要

因为如果不这样定，用户会立刻遇到下面这些困惑：

- 我上传的是 Markdown 文件，为什么它有时是文档，有时是文件
- 我到底是在导入内容，还是在保存原件
- 我之后改的是文档本身，还是原始文件

而“入口决定对象形态”能把这些问题一次性压平。

### 对当前实现的对应关系

当前代码里，`Docs` 入口下的 Markdown 已经是“导入成文档”的语义：

- `.md` 文件会先 `file.text()`
- 然后直接走 `createPage(...)`
- 不会先保留成原始 file 再让用户决定

这条链路在这里：

- [PageExplorerPlaceholder.tsx](/Users/arthur/RustroverProjects/lobehub/src/features/PageExplorer/PageExplorerPlaceholder.tsx#L204)

所以从产品角度，最稳的做法不是再补一个分叉，而是把这条语义正式写清楚：

- `Docs` 导入 Markdown = 创建文档
- `Files` 上传 Markdown = 保存文件

### 如果未来要支持“从 File 生成 Doc”

也必须是显式动作，比如：

- `生成文档`
- `导入为文档`

而不是上传后自动猜测。

### 最终产品表述

建议在方案和后续 UI 文案里统一成一句话：

**在 Docs 中导入，是把内容变成文档；在 Files 中上传，是把内容保存为文件。**

## 八、V2 的信息架构结论

## 结论一句话

**Docs 是知识工作区，Source Set 是知识容器入口，Files 是容器内的资产层。**

### 一级导航

保留双入口：

- `文档`
- `资料集`

不要把二者合并成一个混合入口。

原因：

- 用户进入 `文档`，主要任务是写、读、找文档
- 用户进入 `资料集`，主要任务是整理某个主题下的资产与知识

这两个任务心智不同。

## 九、Docs 工作区的优化方案

## 1. Docs Sidebar 的职责

Docs Sidebar 不再负责展示“全部文档树”，而是只负责：

- 范围选择
- 常用入口
- 快捷切换

推荐结构：

- 搜索
- 未归属
- 全部文档
- 置顶资料集
- 查看全部资料集

长期再补：

- 最近编辑
- 收藏

注意：

- `Sidebar` 里只放高频范围，不放每个资料集下的全部文档
- 资料集只展示置顶项或最近访问项
- “查看全部资料集”进入完整浏览页
- 不建议按“文档数量阈值”自动切换导航模式，信息架构应保持稳定

这更符合飞书式心智：左边是工作区切换器，不是全量知识树。

## 2. Docs 主区的职责

Docs 主区承担两种状态：

### 状态 A：未打开具体文档

主区显示“当前范围下的文档列表页”，而不是默认展示创建卡片空态。

例如：

- 当前选中 `最近编辑`：展示最近文档列表
- 当前选中 `未归属`：展示未归属文档列表
- 当前选中某个资料集：展示该资料集下的文档列表
- 当前选中 `全部文档`：展示文档总表

这点非常关键。

因为在规模化产品里，`/docs` 根页默认展示“创建提示卡”并不够成熟。  
它可以作为空列表时的 empty state，但不应继续作为默认首页。

### 状态 B：已打开具体文档

主区进入编辑器 / 阅读器。

这时 sidebar 保持当前范围高亮，帮助用户知道自己是从哪个工作范围进入这篇文档的。

## 3. Docs 列表的组织方式

当前范围下的列表建议用主区的宽列表，而不是侧边窄列表。

推荐字段：

- 标题
- 所属资料集
- 更新时间
- 类型
- 是否未归属

辅助行为：

- 支持排序
- 支持多选
- 支持批量归属到资料集
- 支持批量移出资料集

## 4. Docs Root 的产品定位

`/docs` 根页不再被定义成“空白创建页”，而应定义成：

**当前工作空间下的文档工作台。**

这会比“文档入口 + 下面一堆新建卡片”更像成熟产品。

## 十、Source Set 工作区的优化方案

## 1. Source Set 首页不是树，而是工作容器入口页

Source Set 首页适合卡片/紧凑列表混合，不适合一上来就是一棵树。

每个资料集入口应展示：

- 名称
- 描述
- 文档数
- 文件数
- 最近更新时间
- 最近活动摘要
- 快捷动作：进入 / 上传 / 新建文档

这一步的作用不是让用户“遍历全部对象”，而是帮助用户选中工作场景。

## 2. 进入 Source Set 后先拆成两个确定有价值的工作面

- `Docs`
- `Files`

这是第一阶段最值得做的拆分，因为它直接解决“知识对象”和“原始资产”混排的问题。

### `Docs`

只展示该资料集下的文档。

这里不展示原始文件，不展示 PDF 列表，不展示素材树。

### `Files`

只展示该资料集下的原始文件与文件夹。

文件树、批量处理、上传、移动等，都发生在这里。

## 3. `Overview` 作为第二阶段评估项，而不是首批强制项

`Overview` 不是没有价值，而是要看 Source Set 在真实使用里是否已经承担“工作场景”角色。

如果当前大多数资料集还更像“装资料的桶”，那一上来做 `Overview` 很容易变成空跳板。

所以更稳的节奏是：

- 第一阶段先做 `Docs / Files`
- 第二阶段再评估是否需要 `Overview`

## 4. 为什么不推荐 Source Set 内默认混合树

因为混合树会把：

- 知识结果
- 原始材料
- 文件夹
- 处理中对象

全部放在同一层上。

短期似乎统一，长期一定变乱。

更成熟的做法是：

- 在容器层统一
- 在工作面层分开

## 十一、对“未归属”的重新定义

`未归属` 不应只是一个普通标签。

更合理的产品定义是：

- `未归属` 是文档整理收件箱
- 它是过渡状态，不是终局状态
- 它应支持快速归档进某个资料集

因此交互上应具备：

- 顶部明确显示数量
- 批量移入资料集
- 在创建后尽量轻量提示是否要归档

但不要强迫用户一开始就必须选资料集。

---

## 十二、对“飞书心智”的真正吸收

飞书式体验的关键不是界面像，而是下面这些机制：

### 1. 全局导航稳定

用户永远知道：

- 我现在在文档
- 还是在资料集

### 2. 当前范围明确

用户要随时知道：

- 我现在看的是最近
- 未归属
- 全部文档
- 还是某个资料集

### 3. 列表和详情分离

用户不会在一个窄栏里同时完成：

- 范围切换
- 对象浏览
- 对象编辑

### 4. 最近和常用优先于全量分类

真正高频使用的，不是所有层级树，而是：

- 最近
- 收藏
- 当前工作集

但对当前仓库来说，`最近 / 收藏` 应放在后续阶段，不应阻塞第一批 IA 改造。

### 5. 容器首页承担认知负担

用户进入某个 Source Set 时，不应该立刻被丢进一棵复杂树。  
应该先通过 `Overview` 理解它是什么，再进入 `Docs` 或 `Files`。

## 十三、对外产品语义建议

不要再对外讲：

- “文档和文件互相转化”

建议统一成下面这套表述：

### 面向用户

- 从文件生成文档
- 查看来源文件
- 在资料集中组织文档和文件
- 将文档归档到资料集
- 将文档导出为文件

### 不建议对外使用

- 文档就是文件
- 文件就是文档
- 文档和文件完全互转

这几句话都会把内部实现的半对称关系暴露成产品承诺，后面会越来越难收。

---

## 十四、URL 与状态建议

为了符合成熟工作区产品的习惯，范围状态需要可深链、可恢复。

### `/docs`

建议支持单一 `scope` 参数：

- `?scope=all`
- `?scope=unassigned`
- `?scope=recent`
- `?scope=favorites`
- `?scope=ss:ss_xxx`

### `source set`

建议支持：

- `/content/source-sets/:id`
- `/content/source-sets/:id/docs`
- `/content/source-sets/:id/files`

而不是只依赖本地 store 判断当前工作面。

---

## 十五、规模化后的设计要求

当文档量和资料集量上升后，设计必须满足这些要求：

### 1. Sidebar 不展示全量对象

否则 100 篇文档、20 个资料集以后就会立刻劣化。

### 2. 大列表放主区

包括：

- 全部文档
- 某资料集下文档
- 未归属文档
- 全部资料集

### 3. 列表支持虚拟化与稳定排序

列表超过一定规模，必须：

- 虚拟化
- 支持固定排序
- 保留查询参数

### 4. 搜索结果按上下文分组

而不是把：

- 文档
- 文件
- 不同资料集来源

全部打成一坨结果。

---

## 十六、建议的最终方案

如果只保留一套最终方案，我建议直接定成下面这样：

### 顶层

- `文档`
- `资料集`

### 文档

- Sidebar：范围切换器
- 主区：当前范围下的文档列表或文档详情

Sidebar 内容：

- 搜索
- 未归属
- 全部文档
- 置顶资料集
- 查看全部资料集

后续增强项：

- 最近编辑
- 收藏

### 资料集

- 首页：卡片/紧凑列表入口
- 内页第一阶段：`Docs / Files`
- 内页第二阶段评估：`Overview`

### 对象关系

- `Doc`：知识对象
- `File`：资产对象
- `Source Set`：容器对象

### 用户语义

- 文件生成文档
- 文档关联来源文件
- 文档与文件共同归属于资料集

## 十七、分阶段落地建议

### Phase 1：先改产品语义和路由状态

- 统一 `Doc / File / Source Set` 语言
- 让 `/docs` 主区从创建型 placeholder 变成 scope 列表工作台
- 用 URL 表达当前 scope

### Phase 2：重做 Docs Sidebar

- 从文档树逐步收敛成范围导航
- 第一批只做未归属、全部文档、置顶资料集、查看全部资料集
- 不把最近、收藏当成首批阻塞项

### Phase 3：完成 Source Set 首批工作区拆分

- 首页卡片化
- 内页先拆 `Docs / Files`

### Phase 4：评估 Overview 与增强范围

- 基于真实使用再决定是否补 `Overview`
- 基于数据模型成熟度补 `最近 / 收藏`

### Phase 5：补齐对象关联体验

- 文件项支持“打开关联文档”
- 文档页支持“查看来源文件”
- 导出与生成分成两个明确动作

---

## 十八、最终定义

可以用一句话把整个产品定义定下来：

**Docs 是面向知识工作的工作区，Source Set 是面向主题组织的容器，Files 是被组织与消费的资料资产层。**

这个定义比“做一棵树”更稳，比“做一堆卡片”更成熟，也更接近飞书式工作区真正有效的那部分心智。
