# 全面性能优化指南

本文面向 LobeHub 技术栈（Next.js、tRPC、Drizzle/PostgreSQL、Vite SPA、React Native 移动端、流式聊天与 Agent），说明**如何系统性地做性能优化**：先量再改、按层级分工、按 ROI 排序。

---

## 1. 原则：先量再改

没有基线的「全面优化」容易变成猜测。建议先建立：

| 层面     | 量什么                                       | 工具 / 方式                                                                |
| -------- | -------------------------------------------- | -------------------------------------------------------------------------- |
| 服务端   | 关键 API 的 P50/P95 延迟、错误率             | OpenTelemetry / APM；tRPC procedure 名或 path 写入 span 属性便于按路由排序 |
| 数据库   | 慢查询、N+1、锁等待                          | `EXPLAIN (ANALYZE, BUFFERS)`、`log_min_duration_statement` 或 APM 的 DB 段 |
| Web 前端 | 首屏、长任务、重渲染                         | Chrome Performance、React Profiler                                         |
| RN       | 列表滚动、JS 帧耗时                          | Hermes、Flipper / 内置性能工具                                             |
| 聊天产品 | 首 token（TTFT）、chunk 间隔、端到端完成时间 | 业务埋点 + 服务端分段计时                                                  |

**默认优先级（无数据时）**：数据库与聊天 I/O → API 序列化与往返 → 前端 bundle 与渲染。

---

## 2. 服务端（Next.js/tRPC / Route Handlers）

| 方向         | 做法                                                                                     | 典型收益                   |
| ------------ | ---------------------------------------------------------------------------------------- | -------------------------- |
| 减少往返     | tRPC 客户端合理开启 batching；`async` 等路由若关闭 batching 须有明确原因（如隔离长任务） | 减少 HTTP 与 JSON 解析次数 |
| 请求内去重   | `createContext` 中避免对同一请求重复解析 cookie / 头；同请求只算一次的值可缓存           | 高 QPS 下更明显            |
| 序列化与体积 | 大列表分页、字段裁剪；避免通过 superjson 传输巨大嵌套结构                                | 中                         |
| 流式响应     | 聊天、导出等保持流式，避免整段缓冲后再写出                                               | 对 TTFT 影响大             |
| 部署拓扑     | 静态与 geo 敏感能力可考虑边缘；强一致、长连接 LLM 仍放主区域                             | 视部署而定                 |
| 运行时       | 合理配置连接池；热路径避免同步解析超大 JSON；关注 `NODE_OPTIONS` 与实例规格              | 中                         |

参考：`src/libs/trpc/lambda/context.ts`、`src/app/(backend)/trpc/*/route.ts`。

---

## 3. 数据库（Drizzle + PostgreSQL）— 往往 ROI 最高

- **索引**：按真实 `WHERE` / `JOIN` / `ORDER BY` 补充复合索引；用 `EXPLAIN (ANALYZE, BUFFERS)` 验证是否走索引、是否大量 Buffer read。
- **N+1**：列表循环内逐条查询 → 改为批量查询或 JOIN / `LATERAL`。
- **分页**：深分页优先 **keyset（cursor）**，避免大 `OFFSET`。
- **连接**：PgBouncer（如 transaction pooling）；应用连接池大小与并发模型匹配，避免排队或打满 DB 连接。
- **读写分离**：读多写少且可接受轻微延迟时，只读查询走副本（复杂度高、收益大）。
- **运维**：`VACUUM`、统计信息；数据量极大时再考虑按时间 / 租户分区。

## 4. 缓存（按一致性要求分层）

| 层级            | 适用场景                           | 注意                                          |
| --------------- | ---------------------------------- | --------------------------------------------- |
| HTTP / CDN      | 静态资源、可公开且短 TTL 的 GET    | 强鉴权接口慎用公共缓存                        |
| 进程内          | 配置、模型列表、权限等读多写少     | 必须定义 TTL 与失效策略                       |
| Redis 等        | 限流、队列结果、会话旁路、热点 key | 与现有 `packages` / `server` 队列能力对齐思路 |
| tRPC / 响应缓存 | 仅对幂等、可接受陈旧的 query       | 需与业务语义、`Cache-Control` 一致            |

原则：优先缓存 **计算或 I/O 昂贵且变更不频繁** 的数据；不要先缓存「本来就很快」的查询。

---

## 5. LLM / Agent 路径（产品体感）

- **并行化**：记忆检索、RAG、工具 schema 组装等在语义允许下用 `Promise.all`，避免无谓串行。
- **上下文裁剪**：历史消息摘要或窗口；工具定义只下发当前需要的部分。
- **模型路由**：简单任务用小 / 快模型，避免一律最大模型。
- **保持流式**：维持 SSE/stream，降低用户感知的「卡住」时间。
- **超时与熔断**：合理超时释放连接与 worker；保护下游与整体容量。

---

## 6. Web SPA（Vite + React）

- **代码分割**：路由与大功能 `lazy` + `Suspense`，控制首屏 chunk。
- **长列表**：虚拟列表；避免单次挂载上千 DOM。
- **状态订阅**：全局 store 使用细粒度 selector，减少无关重渲染。
- **数据请求**：SWR 等配置 `staleTime`、去重、预取，避免重复打同一接口。
- **重依赖**：Markdown / 富文本等按需加载，避免首屏拉满解析栈。

---

## 7. React Native（`apps/mobile`）

- **列表**：`FlashList` 或等价方案；稳定的 `keyExtractor`；行级 `memo`。
- **重渲染**：大组件（如消息气泡）稳定 props 引用，避免父级无关状态导致整列表重绘。
- **图片**：合适分辨率与缓存策略；控制列表内同时解码数量。
- **JS 线程**：大 JSON 解析、重同步逻辑可延后到 `InteractionManager` 或拆任务。
- **Hermes**：保持开启；用 **release** 配置测卡顿与启动。

---

## 8. 构建与交付

- CI：目录 / 包级增量 type-check 与测试，缩短反馈（避免默认全量长测拖慢迭代）。
- 产物：bundle 分析（rollup/vite analyzer），移除未使用依赖与重复 polyfill。
- 静态资源：CDN、现代图片格式、字体子集化。

---

## 9. 建议落地顺序

1. **打点**：选定 3 条核心路径（例如：会话列表、发送消息、设置 / 模型列表）。
2. **每条路径**：DB `EXPLAIN` → 消除 N+1 / 补索引 → 再考虑缓存。
3. **聊天**：并行 I/O、上下文裁剪、流式保持。
4. **前端**：首屏 chunk、列表与重渲染。
5. **再评估**：读写分离、大范围 Redis、服务拆分 —— 多数团队在 1–4 步已有显著收益。

---

## 10. 与「架构重构」的关系

分层（用例层、瘦 router）**本身不直接提升性能**；它让性能工作更容易做对（例如集中加缓存、批量查询、单测防回归）。性能数字来自：**更少的 I/O、更聪明的查询、更小的传输与渲染**，而不是多一层目录。
